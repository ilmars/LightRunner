# Operator page restyle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the designer's restyle of the operator page (and the phone, tokens, font and icon), with Prepare replacing Preview and Blind, Individual lights, and a "Who to call" setting.

**Architecture:** Mostly page work in `web/operator/` and `web/shared/theme.css`, built from the designer's mockups (`.dc.html` files copied into the plan workspace under `mockup/`; their inline styles and wording are the reference). Prepare reuses the Blind draft machinery on the server; Individual lights uses the engine's manual control.

**Tech Stack:** Node 24 (type stripping), TypeScript (erasable syntax only), zod, node:test, plain HTML/JS/CSS (no framework).

**Spec:** [docs/superpowers/specs/2026-10-20-restyle-design.md](../specs/2026-10-20-restyle-design.md)

## Global Constraints

- Branch `restyle` from `main`; main checkout, no worktree; never push.
- The mockups are the reference for layout, sizes, colours and wording: `<workspace>/mockup/project/Main.dc.html` (Live, Prepare, picker, colour editor, effect editor, individual lights: the `panel` and `mode` values), `Phone.dc.html`, `Icon.dc.html`. Copy values from them; the spec wins where they differ.
- Every input stays a Command through `App.command()`; the server is the single source of truth; the engine stays pure.
- TypeScript erasable syntax only, `.ts` imports, `import type`.
- Web: 44 px targets (52 px in the bottom bar), plain words, sentence case for UI text, nothing bright (tints ≤ 26 %, accent only as 1–2 px lines). No network fonts: Inter is served by Light Runner.
- `npm test`, `npm run typecheck`, `npm run jump-check` pass before every commit.
- Each task updates `docs/STATUS.md`, and `docs/design-system.md` when it changes a pattern; DECISIONS gets a 20 Oct line for each call.
- Browser checks at 1080 × 810 (phone 390 × 844) on your own server (`LIGHT_RUNNER_OUTPUT=none`, a temp data dir with `shows/stage-l1.json` loaded, a port of your own); never touch the servers on 8092/8093; no console errors.

## Review Focus

1. Prepare: nothing reaches the lights until Go; Save stores the draft; Live drops it; two tablets, one preparing — the other never sees the draft. (Task 1)
2. A tablet that was in Preview or Blind when the page updates comes back in Live with nothing lost from the real stage. (Task 1)
3. The restyle keeps every existing control reachable (Back to, Save hold, Flash per group, smoke slider and Puff, tempo menu, Fade menu, Undo, Edit list, quick look Edit). (Tasks 2–5)
4. Individual lights: a held light never jumps when picked, changed or released; Release all clears every hold; Basic lights and Blackout clear holds as today. (Task 6)
5. The phone layout still works at 390 × 844 and on its side. (Task 7)

### Task 10: Saturation and exact colour values (owner request, 21 Oct)

**Files:** `web/operator/*` (colour editor, Any colour, effect editor own colours); shared/server only if a colour can't be expressed today.

- **Saturation**: a fill slider under every colour strip (colour editor, Any colour, own colours in the effect editor), from grey (0 %) to the strip's full colour (100 %). The strip picks the hue, Saturation pales it, Brightness stays as today. A white-only group (warm-to-cool strip) has no Saturation.
- **Exact values ›**: folded by default under the strip; open, it shows a hex field (`#RRGGBB`) and R, G, B number fields 0–255 (`inputmode="numeric"`, 44 px, design-system fields). Typing updates the strip marker, Saturation, swatch and preview, and moving the strip or Saturation updates the fields. Invalid input is refused with a quiet note and the field goes back. Nothing reaches the stage until Save (the colour editor); Any colour follows its existing live rules (sends as you change, throttled, Prepare wraps it).
- Hue/saturation are derived from the RGB value (one source of truth: the hex), so a typed colour that isn't on the strip still round-trips exactly.
- [ ] Implement; browser-check typing hex and RGB, Saturation drag, round trip (type → reopen shows the same values), Any colour live, Prepare, a white-only group, the phone (no exact values on the phone if the picker has no editor there).
- [ ] Run tests, typecheck, jump-check; docs (STATUS, DECISIONS, design-system); commit "Colours: saturation and exact values".

### Task 11: Controller keys — assign MIDI keys to actions, songs and quick looks (owner request, 21 Oct; after Task 9)

A short design (spec) is written and agreed first; this is the outline the owner gave.

- **Any MIDI controller, not only the APC mini.** A key is a MIDI note or a control change (fader/knob) on a connected device. The APC mini's standard layout (today's fixed mapping) is a ready-made starting point; another controller starts empty.
- **Settings › Controller keys** (a page or card in the new look): the fixed actions — Next, Back to, Undo, Basic lights, Blackout (hold), Flash all / per group (hold), Fade, Tempo Tap, Master, group dimmers, Prepare/Live, Go — each with "Press a key to assign" (learn: the next key pressed on the controller is taken), Clear, and what it is now ("APC mini · pad 3,2"). "Reset to the APC mini layout".
- **Songs and quick looks are assigned where they are edited**: running-order Edit and the quick-look Edit sheet each get a "Controller key" row with the same learn / clear. A key belongs to one thing; assigning it elsewhere moves it (with a quiet note).
- Positional rules stay available ("pads in rows 1–2 follow the running order", "column N = group N's colours") as switches in Settings, so the APC mini works with no setup.
- Feedback lights (on stage / next / running colour) for controllers that support them (APC mini, mk2 colours); other controllers simply get no lights.
- Saved with the show; everything still becomes the same Commands through `App.command()`.
